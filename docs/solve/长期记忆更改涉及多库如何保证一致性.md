# 长期记忆的事务、投影与恢复边界

更新于 2026-10-31。本文描述当前实现，历史设计目标见 `../superpowers/plans/2026-07-26-long-term-memory-eventual-consistency.md`。

## 事实源和提交顺序

PostgreSQL 保存权威长期记忆状态。`internal/infrastructure/persistence/memorytx` 在本地事务中处理记忆版本、审计关系与 Outbox 事件。应用先计算候选、检查归属及内容策略，事务成功后才把已提交变化应用到内存；失败不能先污染缓存。用户偏好仍是独立的 best-effort 写入，不属于同一个事务。

Milvus 和 Neo4j 是派生投影。记忆携带稳定标识、版本、内容哈希、用户归属和删除状态；事件承载完整状态。旧版本跳过、重复相同状态幂等、冲突需报告，不能仅凭“收到事件”视为已落库。

## Outbox 与投影

`memoryoutbox` 保存待处理事件、领取状态、重试和失败信息。`application/memoryprojection` 驱动目标投影，`infrastructure/projection/versioned` 规范应用结果，Milvus/Neo4j 适配器执行目标写入。失败重试有上限，死事件和缓存恢复需要运营处理。

投递为至少一次。当前领取/确认缺少跨进程 fencing，截止时间只能减少过期工作，不能保证原子所有权；Milvus 多实例没有 CAS。因此部署限定每个目标一个活跃消费者，Milvus 保持单写者，不能宣称多实例 exactly-once 或有限时间内必然收敛。

## 对账

`application/memoryreconcile` 比较源与目标的 ID、版本、内容哈希和删除状态，把修复重新写入 Outbox，不直接旁路改目标。仅已处理的修复可按规则重新入队，重复/冲突/跳过分别报告。

全量扫描不是源/目标的一致快照，并在内存暂存记录。真实 Milvus 游标顺序、强一致集合、并发孤儿复核、dead 事件处理和每关系漂移修复仍需联调。缓存补偿也不等同于跨进程实时一致。

## 与文档索引的区别

上述事务针对长期记忆。文档文件、PG 文本块、Milvus、Elasticsearch 和异步知识图谱另有写入链路，没有共享的跨库事务。文档 indexed_count 不能用来证明记忆投影或全部文档索引完成。

## 验证与运维

仓库测试覆盖事务回滚、用户归属、版本/删除、事件序列化、领取/重试、投影冲突和修复逻辑，使用 mock/内存实现。真实 PostgreSQL schema、SQL 隔离、Milvus/Neo4j 查询兼容性、断线重启、积压及备份恢复尚未执行。

部署前应以合成数据进行重复投递、过期租约、目标写入成功但确认失败、删除漂移、死事件修复和重启检查；同时监控积压、重试、死事件、冲突和修复计数。不得为了清理积压直接丢弃权威源或强制覆盖更高版本。
